# SpaceGravitySimulator — Техническая спецификация

Область: двумерный ньютоновский N-body физический движок (попарная гравитация) с
визуализацией в немедленном режиме, написанный с нуля на .NET. Документ описывает код в
состоянии `master` @ `a8f6e8d` и предназначен для проведения аудита. Каждое утверждение
ниже отслеживается до конкретного файла и диапазона строк. Не описывается ни одно
проектное намерение, которое не реализовано.

---

## 1. Обзор проекта

Автономное консольное приложение, интегрирующее уравнения гравитационного движения
для набора точечных масс в двумерной плоскости и отображающее результат в реальном
времени.

**Функциональная область**

- Ньютоновская попарная гравитация, прямой суммарный подсчёт, O(n²), со смягчением по
  Плуммеру.
- Интегрирование методом Velocity Verlet с настраиваемым числом подшагов.
- Отрисовка тел в реальном времени и накопленных орбитальных следов.
- Интерактивная камера (зум к курсору, панорамирование правой кнопкой) и слайдер
  `TimeScale` в диапазоне `[0, 1000]`.
- Точность вычислений является параметром-константой дженерика; в поставляемой
  конфигурации используется `double`.

**Явно вне области** (в коде отсутствует): пространственное разбиение, код Бабса —
Хатта или любые другие деревья, обработка столкновений, твёрдые тела, сериализация и
сохранение состояния, удаление сущностей, упаковка движка в библиотеку (проект имеет
`OutputType=Exe`).

**Нефункциональные характеристики**

- Физическое состояние не порождает аллокаций в установившемся режиме (единственное
  исключение — см. F-03 в §7).
- Слой рендеринга полностью отделён от физического: рендереры принимают `Span<T>` /
  `ReadOnlySpan<T>` и никогда не обращаются к `World<T>`.
- Ядро движка (`World`, `Components`, `Services/GravityService`, `Services/MovementService`)
  не содержит ссылок на Raylib и потому независимо покрывается юнит-тестами.

**Замечание о физической достоверности.** Используемый пресет (`Program.cs:47–76`)
использует `G = 0.0001`, `M_sun = 100000`, пиксельный масштаб `650 px/а.е.` и
подобранный вручную `speedFactor = 0.7` (`Program.cs:56`, помечен
`// <--- МЕНЯЙ ЭТО ЧИСЛО`). Начальные круговые скорости поэтому не согласованы с
реальным соотношением `sqrt(GM/r)` для этих единиц. Пресет нормализован по масштабу для
визуализации, а не калиброван астрономически. Построчный комментарий `// =1` в
`Program.cs:47` неверен: `G` равно `0.0001`.

## 4. Техническая архитектура

### 4.1 Data-Oriented Design (SoA)

Состояние хранится по столбцам, а не в виде объектов на сущность.
`ComponentStorage<T>` (`Components/ComponentStorage.cs:11–17`) объявляет семь плоских
массивов — по одному на каждый скалярный компонент, все индексируются по ID сущности:

```
_positionsX[]  _positionsY[]  _masses[]
_velocitiesX[] _velocitiesY[]
_accelerationX[] _accelerationY[]
```

Не существует ни `struct Body { float X, Y, Mass, Vx, Vy, ... }`, ни заголовков объектов
на тело. Следствия, важные для аудита:

- **Единообразный шаблон доступа.** Каждая система линейно проходит целый столбец — это
  именно тот шаблон доступа, который наиболее эффективно обрабатывают аппаратные
  предзагрузчики и SIMD-блоки. Использование строк кэша максимально: чтение N
  Y-координат затрагивает ровно необходимые байты.
- **Отсутствие переходов по указателям.** Нет индирекции «сущность → объект», поэтому
  стоимость итерации не зависит ни от раскладки кучи, ни от состояния GC.
- **Векторизуемые столбцы.** Поскольку столбец непрерывен и плотен, он напрямую
  потребляется `System.Numerics.Vector<T>` (§4.2). Раскладка AoS потребовала бы инструкций
  gather или загрузок со страйдом.
- **Сущности — чистые индексы.** `Entity` (`Entities/Entity.cs:7`) — `ref struct` с одним
  полем `int`. Его нельзя упаковать в boxing, поместить в массив или захватить в лямбду.
  Это осознанное и проверяемое компилятором выражение DOD-намерения: система типов
  запрещает случайный уход в кучу. Побочный эффект — такую схему нельзя использовать с
  `async`, в обобщённых ограничениях или с рефлексией без переработки.

**Дескрипторы выдаются из предвыделенного пула.** `World<T>` заполняет `Queue<int>`
последовательными ID от 0 до 10 000 в конструкторе (`World.cs:35`), а `CreateEntity()`
(`World.cs:37–41`) извлекает из него очередной. Поэтому ID плотные и нумеруются с нуля —
это необходимое условие для SIMD-нарезки в §4.2 и для использования количества сущностей
как границы цикла.

**Рост ёмкости.** `EnsureCapacity(int id)` (`ComponentStorage.cs:34–47`) удваивает ёмкость
до превышения `id` и перевыделяет массивы. Этот путь неполон — см. F-01, находку
наивысшей серьёзности в этом документе.

**API доступа.** Запись идёт через `SetPosition` / `SetMass` / `SetVelocity` /
`SetAcceleration`, каждая из которых сначала вызывает `EnsureCapacity`. Чтение получает
изменяемые `Span<T>` или парные span-представления:

```csharp
CoordinatesView<T> GetRawCoordinates(int count) => new(_positionsX.AsSpan(0, count), _positionsY.AsSpan(0, count));
Span<T>            GetMasses(int count)         => _masses.AsSpan<T>(0, count);
VelocitiesView<T>  GetRawVelocities(int count)  => new(_velocitiesX.AsSpan<T>(0, count), _velocitiesY.AsSpan<T>(0, count));
AccelerationsView<T> GetRawAccelerations(int count) => new(_accelerationX.AsSpan<T>(0, count), _accelerationY.AsSpan<T>(0, count));
```

`AsSpan` возвращает представление над существующим массивом; копирования и аллокаций нет.
Парные `ref struct`-представления существуют, чтобы вернуть два span из одного вызова без
аллокации кортежа в куче и чтобы зафиксировать намерение на «только чтение» у аксессоров
с префиксом `Raw`.

Эти аксессторы выдают **изменяемые** span внутрь приватных массивов. Системы, следовательно,
пишут состояние компонентов напрямую через возвращённые представления — именно так
`HalfStep` мутирует скорость и позицию (`MovementService.cs:38–41`), а `Update` пишет
ускорение (`GravityService.cs:94–95`) без обращения к сеттерам. Плата за это: на границе
хранилища невозможно обеспечить ни один инвариант; валидация — обязанность вызывающего.

### 4.2 SIMD-векторизация

`GravityService<T>.Update` (`Services/GravityService.cs:12–98`) — единственная ручная
векторизация в проекте. Цикл построен так, что **внутренний** цикл векторизуется по
*целевым* телам, а **внешний** обрабатывает одно *исходное* тело. Ширина регистра
определяется во время выполнения, поэтому код адаптируется к железу, а не хардкодит ISA:

```csharp
var step = Vector<T>.Count;   // GravityService.cs:14 — например, 4 для double на AVX2, 8 для float
```

**Векторные константы** вынесены за оба цикла и заполняются одним значением (broadcast) раз
за вызов (`GravityService.cs:19–21`): `vG`, `vEpsilon = 0.01`, `vOne = 1`.

**Векторизованный цикл накопления** (`GravityService.cs:56–78`) проходит по массивам целей
блоками шириной в регистр и выполняет на блок:

```csharp
var vDX     = vXB - vXA;                              // GravityService.cs:62
var vDY     = vYB - vYA;                              // :63
var vDistSq = (vDX * vDX) + (vDY * vDY) + vEpsilon;   // :65  обратный квадрат + смягчение
var vInvDist = Vector.SquareRoot(vOne / vDistSq);     // :67  1 / sqrt(r²)
var vMag     = (vG * vMassB / vDistSq) * vInvDist;    // :68  G·m / r²  ·  r̂
vTotalAccX += vDX * vMag;                             // :76
vTotalAccY += vDY * vMag;                             // :77
```

Это стандартный смягчённый закон обратных квадратов: `a = G·m·r⃗ / |r|³`, выраженный как
`(G·m/r²)·(r⃗/|r|)`. Обратный квадратный корень получается одним аппаратным извлечением
корня и одним делением на вектор вместо операций на каждый элемент.

**Горизонтальное суммирование.** Для каждого исходного тела векторный аккумулятор
схлопывается через `Vector.Sum` (`GravityService.cs:80–81`) до присоединения
скалярного остатка.

**Ветвление-безопасное исключение взаимодействия с самим собой.** Тело не должно
притягивать само себя. В коде это обеспечивают три независимых механизма, ни один из
которых не вносит ветвления по данным внутрь векторного тела:

1. **Аддитивное смягчение.** `+ vEpsilon` в квадрате расстояния (`:65`) гарантирует
   ненулевой делитель, поэтому векторное деление всегда определено. Цена — *длина
   смягчения*: силы подавляются для расстояний меньше `sqrt(ε)`.
2. **Диагональные маски дорожек.** `GravityService.cs:37–44` заранее вычисляет для каждого
   смещения дорожки `k ∈ [0, step)` вектор `Vector<T>`, равный `T.One` во всех дорожках,
   кроме дорожки `k`, где он равен `T.Zero`. Эти векторы образуют тождественный оператор
   «обнулить дорожку k».
3. **Маскирование величины.** Когда текущий блок целей `[j, j+step)` содержит индекс
   источника `i`, маска применяется мультипликативно ко всему вектору величин
   (`GravityService.cs:70–74`):

   ```csharp
   if (i >= j && i < j + step) {
       int offset = i - j;
       vMag *= masks[offset];
   }
   ```

   Одно ветвление на *блок* здесь неизбежно (предикат относится к индексу цикла, а не к
   данным), но эффект не зависит от данных: дорожка «с самим собой» даёт ровно
   `0 * r⃗ = 0` в аккумулятор, и проверка `r == 0` не исполняется ни разу на элемент.
   Маска применяется к `vMag`, а не к смещению, поэтому обнуление распространяется и на
   скалярное умножение, и на накопленную сумму.

**Обработка остатка.** SIMD-цикл выполняется, пока `j < n - step` (`:56`), а скалярный
цикл обрабатывает оставшиеся менее `step` элементов (`:83–93`) с проверкой
`if (j == i) continue;`. Вместе они покрывают ровно `[0, n)` без перекрытий. Поскольку
граница строгая (`<`), при точном кратном `step` последний полный блок обрабатывается
скалярным путём — небольшая потеря пропускной способности, а не ошибка корректности.

**Стоимость построения векторов.** Внутренний цикл материализует источники через
конструктор `Vector<T>(Span<T>)` — `new Vector<T>(masses.Slice(j))` (`:58–60`). Эти
значения живут на стеке, аллокаций нет, но конструктор от span копирует поэлементно, а не
переинтерпретирует массив; невыровненная переинтерпретация базового `T[]` избавила бы от
копирования. Дефекта корректности это не создаёт.

**Мёртвый код в этом методе** (проверено — всё неиспользуемо): `vMassA` (`:48`, вычисляется
и не читается) и `vLimit` (`:36`, объявлен и не используется). `epsilon` (`:16`)
используется только скалярным остатком, а не векторным путём — см. F-02.

**Сложность.** Прямое суммирование — O(n²) и по числу тел, и по ширине регистра.
Аппроксимации, отсечения и списков соседей нет, поэтому точность не приносится в жертву
скорости; потолок задаёт цикл подшагов из §5.

### 4.3 Обобщённая математика (Generic Math)

Каждый тип движка параметризован скалярным типом с ограничением

```csharp
where T : notnull, INumber<T>, IConvertible
```

применённым к `World<T>`, `ComponentStorage<T>`, `GravityService<T>`,
`MovementService<T>`, `VisualizationService<T>`, `UIService<T>` и `CameraController<T>`
(у `EntityRenderer.Render<T>` более узкое `where T : INumber<T>, IConvertible`).

`INumber<T>` — абстракция обобщённой математики .NET, дающая полный поверхностный набор
арифметики — `+`, `-`, `*`, `/`, сравнения, — а также статические вспомогательные методы
преобразования, которые использует код. Конкретные инстанцирования в репозитории:
`World<double>`, `MovementService<double>`, `GravityService<double>`,
`VisualizationService<double>` (`Program.cs:12–15`) и `ComponentStorage<double>` в тестах.

**Преобразование между `T` и типами рендеринга.** Движок обобщён по `T`, но Raylib и
`System.Numerics.Vector2` — конкретные типы. Используются три разных маршрута
преобразования, и они не унифицированы:

| Назначение | API | Место |
|---|---|---|
| Скаляр → `T` из литерала | `T.CreateChecked(0.5f)` | `MovementService.cs:38–39,57–58` |
| `T` → `float` (рендеринг) | `float.CreateTruncating(posX[i])` | `TrailRenderer.cs:99–100` |
| `T` → `int` (`DrawCircle` в Raylib) | `int.CreateChecked<T>(coordX[i])` | `EntityRenderer.cs:19` |
| `T` → `double` (скалярный `sqrt`) | `double.CreateChecked<T>(distSq)` | `GravityService.cs:89` |

`IConvertible` присутствует в наборе ограничений ради методов сужения/расширения; в
современном .NET он в значительной мере избыточен, поскольку `INumber<T>` уже наследует
`INumberBase<T>`. `T.CreateChecked` используется в режиме `checked` повсеместно, поэтому
выход за диапазон приводит к исключению, а не к насыщению, — последствия отмечены в
F-05 и F-11.

**Выбор точности — один аргумент типа.** Движок инстанцируется один раз, в
`Program.cs:12–15`. Перевод симуляции с `double` на `float` — правка в четыре токена:
арифметическая ширина уменьшается вдвое, а пропускная способность SIMD примерно
удваивается (`Vector<float>.Count` вдвое больше `Vector<double>.Count` на AVX2). Тесты прогоняют те же
типы через `ComponentStorage<double>`, `GravityService<double>` и
`MovementService<double>`, поэтому обобщённая поверхность покрыта хотя бы для одной
инстанциации.

**Цена абстракции.** Обобщённый код над `INumber<T>` компилируется по одному экземпляру на
каждый тип-значение; `T` здесь всегда структура, поэтому разделяемой generic-упаковки не
возникает. Реальная цена — многословность вызовов `CreateChecked` / `CreateTruncating` у
каждого числового литерала и необходимость в `Camera2DExtension.SetZoom<T>` как мосте
между generic и `Vector2` — который при этом не используется (F-08).

### 4.4 Симплектическое интегрирование

`MovementService<T>` (`Services/MovementService.cs`) реализует двухфазную схему
«удар — дрейф — удар», известную как **Velocity Verlet**. Схема симплектическая и потому
сохраняет энергию в ограниченных пределах для используемого здесь сепарабельного
гамильтониана (гравитация зависит только от координат).

Две фазы — отдельные публичные методы, вызываемые из кадрового цикла в обязательном
порядке (`Program.cs:92–94`):

```
HalfStep(world, dt)  →  GravityService.Update(world)  →  SecondHalf(world, dt)
```

**Фаза 1 — первый удар и дрейф** (`MovementService.cs:20–43`):

```csharp
_prevAccX[i] = accX[i];                     // :35  снимок a_n
velX[i] += accX[i] * (dt * T.CreateChecked(0.5));   // :38  v ← v_n + a_n·dt/2  = v_{n+1/2}
coordX[i] += velX[i] * dt;                  // :40  x ← x_n + v_{n+1/2}·dt = x_{n+1}
```

**Пересчёт сил** происходит между фазами, в новых координатах, перезаписывая столбец
ускорений на месте.

**Фаза 2 — второй удар через разность ускорений** (`MovementService.cs:45–60`):

```csharp
velX[i] += (accX[i] - _prevAccX[i]) * (dt * T.CreateChecked(0.5));   // :57
```

Это алгебраически тождественно каноническому второму удару
`v_{n+1} = v_{n+1/2} + a_{n+1}·dt/2`:

```
v_{n+1/2} + (a_{n+1} − a_n)·dt/2
  = (v_n + a_n·dt/2) + (a_{n+1}·dt/2 − a_n·dt/2)
  = v_n + a_{n+1}·dt/2        ✓
```

Разностная форма выбрана, чтобы переиспользовать уже продвинутую скорость, но она
вводит вычитание двух близких по величине ускорений. Там, где
`|a_{n+1} − a_n| ≪ |a_n|`, это вычитание близких чисел и второй удар теряет точность
относительно канонической формы. См. F-06.

**Неявный контракт между фазами.** `SecondHalf` корректен только непосредственно после
`HalfStep` и при том же количестве тел. Сервис хранит `_prevAccX/_prevAccY` как состояние
экземпляра, размер которого задаётся конструктором (`MovementService.cs:11–18`,
в `Program.cs:13` передаётся `10000`), и **не проверяет** его против
`GetActiveEntities()`. Ни требование порядка, ни требование размера не выражены ни системой
типов, ни проверкой. См. F-10.

**Почему здесь симплектично.** Поскольку все некинетические члены являются функциями
только координат, а схема вычисляет силу в `x_{n+1}` и корректирует скорость изменением
силы, обновление обратимо во времени и сохраняет скрытый гамильтониан. Энергия колеблется
внутри ограниченной огибающей, а не дрейфует монотонно. Симплектичность обусловлена
корректной и *согласованной* константой смягчения; несогласованность, описанная в F-02,
нарушает симметрию эффективного потенциала на границе векторного и скалярного путей.

Юнит-тест `SecondHalf_UpdatesVelocityUsingAccelerationChange` (`Test1.cs:168–187`)
фиксирует арифметику разностной формулировки против эквивалентного выражения
`v + a_old·dt/2 + (a_new − a_old)·dt/2`, подтверждая, что эквивалентность осознанна и
задумана.

### 4.5 Конвейер рендеринга

Слой рендеринга — отдельное дерево композиции с корнем `VisualizationService<T>`
(`Services/VisualizationService.cs:11`), владеющим пятью коллабораторами и ничего не
знающим об интегрировании. Инстанцируется один раз в `Program.cs:15` с областью
1000×1000.

**Покадровая последовательность** (`VisualizationService.Update`,
`VisualizationService.cs:28–50`):

```
1. GetActiveEntities() → n; получить span-ы coordX, coordY, масс   (:30–34)
2. CameraController.Update()                    — ввод → состояние камеры  (:36)
3. TrailRenderer.Update(coordX, coordY, masses, n) — выборка истории следов (:37)
4. UIService.Update(world)                      — передать TimeScale в мир (:38)
5. WindowManager.BeginDrawing / ClearBackground(White)              (:40–41)
6. BeginMode2D(camera)                                                (:42)
7.   TrailRenderer.Render()                                          (:44)
8.   EntityRenderer.Render(coordX, coordY, masses, n)                (:45)
9. EndMode2D                                                         (:47)
10. UIService.Draw()      — пространство экрана, вне трансформации камеры (:48)

```

Шаги 2–4 — изменение состояния, 5–11 — вывод. Следы рисуются раньше тел, чтобы корректно
перекрываться дисками. UI рисуется вне `BeginMode2D`/`EndMode2D`, поэтому виджеты не
подвержены панорамированию и зуму.

`WindowManager` (`Services/Visualization/WindowManager.cs`) инкапсулирует жизненный цикл
Raylib: `InitWindow` + `SetTargetFPS(60)` в конструкторе (`:12–13`), тонкие прокси для
`BeginDrawing`/`EndDrawing`/`BeginMode2D`/`EndMode2D`/`ClearBackground`/`ShouldClose` и
`Dispose()`, вызывающий `Close()` (`:19`) — но не реализующий `IDisposable` и никогда не
вызываемый (F-12).

**Хранилище следов — плоский кольцевой буфер.** `TrailRenderer`
(`TrailRenderer.cs:65–129`) выделяет один непрерывный `Vector2[]` размером
`maxBodies * maxTrailLength` (200 × 500 = 100 000 элементов, ≈ 800 КБ) плюс `int[]` с
индексами голов по телам (`:79–80`). Тело `i` владеет непрерывным срезом
`[i * maxTrailLength, (i+1) * maxTrailLength)`, а его курсор записи сдвигается по модулю
длины следа каждые `_updateStep` кадров (`:95`). Такая раскладка сохраняет историю каждого
тела непрерывной в памяти и превращает выборку в одну запись без сдвига массива —
предыдущая реализация, всё ещё сохранённая как закомментированный блок в
`TrailRenderer.cs:1–59`, сдвигала весь массив на каждой выборке.

`Update<T>` принимает `ReadOnlySpan<T>` и ограничен по кадрам:
`if (++_frameCounter % _updateStep != 0) return;` (`:86–87`). Тела с нулевой массой
пропускаются (`:93`) и, что важно, их голова **не** продвигается, поэтому их срез сохраняет
начальную инициализацию `Vector2.Zero`. `Render` затем полагается на
`p1 != Vector2.Zero && p2 != Vector2.Zero` (`:122`), чтобы не рисовать отрезки в
неинициализированную память — это соглашение на основе значения-маркера, а не флага
валидности. При отрисовке пропускается отрезок, пересекающий голову (`:114`), чтобы не
соединять новую выборку с самой старой через шов кольца.

`Render` обходит все тела и все слоты на каждом кадре:
`_maxTrails * (_maxTrailLength - 1)` ≈ 99 800 кандидатов в отрезки, каждый из которых —
потенциальный немедленный вызов `DrawLineV` (`:105–128`). Это доминирующая стоимость
кадра в слое рендеринга. См. F-04.

**Отрисовка тел.** `EntityRenderer.Render<T>` (`EntityRenderer.cs:11–22`) выводит радиус
из массы по логарифмической шкале — `2f + log10(mass + 1) * 3f` (`:16`), — чтобы Солнце
(`10⁵`) и Меркурий (`0.055`) были видны при одном зуме, и пропускает неположительные массы
(`:15`). Оттенок задаётся как `(i * 137.5f) % 360` (`:17`) — распределение по золотому углу,
максимизирующее перцептивное различие соседних индексов, — и преобразуется через
`ColorFromHSV`. Координаты преобразуются через `int.CreateChecked<T>` (`:19`), то есть
усекаются до целых пикселей до передачи в `DrawCircle` Raylib, принимающего целочисленные
координаты; `DrawCircleV` сохранил бы субпиксельную точность. См. F-05.

**Камера.** `CameraController<T>` (`Services/Visualization/CameraController.cs:11–27`)
инициализирует `Camera2D` с `Zoom = 1`, причём и `Offset`, и `Target` устанавливаются в
центр области просмотра; затем `Update()` запускает два независимых обработчика.
`HandleZoom` (`:35–44`) корректно реализует зум к курсору: переводит позицию мыши в
мировые координаты до и после применения ограниченного приращения зума и сдвигает
`Target` на разницу мировых координат, чтобы точка под курсором оставалась неподвижной.
Зум ограничен `[0.1, 10]`. `HandlePanning` (`:46–66`) панорамирует по зажатой правой кнопке
мыши и делит экранную дельту на `Zoom` (`:58`), поэтому длина перетаскивания не зависит от
зума. Демпфирования, инерции и границ панорамирования нет.

Публичный аксессор `Camera` возвращает `Camera2D` **по значению** (`:14`); поскольку
`Camera2D` — структура, мутация возвращённого значения вызывающим не имеет эффекта.
Закомментированная строка `//public ref Camera2D Camera => ref field;` на позиции `:15`
показывает, что это было замечено. Текущая точка вызова (`VisualizationService.cs:42`)
только читает значение, поэтому сегодня поведение корректно (F-13).

**UI.** `UIService<T>` (`Services/UIService.cs`) владеет единственным `Slider`,
размещённым в `(screenWidth - 250, 20, 200, 20)` с диапазоном `[0, 1000]` и значением по
умолчанию `1.0` (`UIService.cs:16–23`). Каждый кадр виджет обновляется, и его значение
передаётся в мир: `world.SetTimeScale(T.CreateChecked(_timeScaleSlider.CurrentValue))`
(`:28`). `Slider` (`Services/UI/Slider.cs`) реализует наведение → начало перетаскивания →
отпускание (`Update`, `:17–34`) и отображает X-координату указателя в нормализованное
значение, ограниченное `[0,1]` (`:30–32`); `Draw` (`:36–44`) рисует дорожку и ползунок
шириной 10 px.

**Члены расширений.** `Extensions/Camera2DExtension.cs:9–16` использует синтаксис блока
`extension(Camera2D camera)` языка C# 14, добавляя `SetZoom<T>` и `SetTarget<T>`. Это

(строка `:14`), то есть накопление, а не присваивание.

## 5. Кадровый цикл и подшаги

`Program.cs:78–99` — основной цикл:

```csharp
var frametime = Raylib.GetFrameTime() * world.GetTimeScale();
var safeStep  = 0.01f;
int subSteps  = (int)Math.Ceiling(frametime / safeStep);
if (subSteps <= 0) subSteps = 1;
var stepDt = frametime / subSteps;

for (int i = 0; i < subSteps; i++) {
    movementSystem.HalfStep(world, stepDt);
    gravitySystem.Update(world);
    movementSystem.SecondHalf(world, stepDt);
}
visualisationSystem.Update(world);
```

Интегрирование отделено от частоты кадров: кадр делится на подшаги с максимальной
длительностью `0.01` единиц времени, что удерживает симплектический интегратор в пределах
его области устойчивости независимо от длительности кадра. `TimeScale` (управляемый из UI,
`[0, 1000]`) масштабирует симулируемое время на кадр, поэтому на один кадр приходится
пропорционально больше симулируемого времени; `subSteps` растёт соответственно, а
`stepDt` внутри подшага остаётся ограниченным `safeStep`. Это связывает стоимость
рендеринга с настройкой `TimeScale`.

Два замечания к этому циклу: `subSteps` **не ограничен сверху** (F-14), а отрицательный
`frametime` даёт `subSteps = 1` через указанную проверку.

## 7. Находки аудита

Упорядочены по серьёзности. Все выявлены чтением кода; F-01 подтверждён выводом сборки.
Ничто здесь не является стилистическим предпочтением — каждый пункт представляет собой
риск поведения или ёмкости.

### F-01 — `EnsureCapacity` перевыделяет 3 массива из 7. **Серьёзность: высокая.**
`Components/ComponentStorage.cs:34–47` перевыделяет только `_positionsX`, `_positionsY` и
`_masses`. Массивы `_velocitiesX`, `_velocitiesY`, `_accelerationX`, `_accelerationY`
сохраняют прежнюю длину; строка `:44` — буквальный маркер `// Resize остальных...`.

Последствия, все достижимые при нормальной работе:
- `SetVelocity(id, ...)` / `SetAcceleration(id, ...)` при `id >= _capacity` выбрасывают
  `IndexOutOfRangeException` (запись происходит *после* возврата `EnsureCapacity`, поэтому
  никакая проверка её не перехватит).
- `GetRawVelocities(n)` / `GetRawAccelerations(n)` при `n > _capacity` выбрасывают
  исключение из `AsSpan(0, count)`. Поскольку все системы берут `n` из
  `GetActiveEntities()`, первый физический шаг после создания 1024-й сущности уже
  приводит к исключению — до того как какому-либо телу потребуется двигаться.

Сейчас не проявляется: поставляемый пресет создаёт 9 сущностей. Любая конфигурация выше
`initialCapacity` (по умолчанию 1024) падает на первом подшаге. Исправление:
перевыделять все семь массивов в теле `EnsureCapacity`.

### F-02 — Две разные константы смягчения в одном цикле сил. **Серьёзность: высокая.**
`GravityService.cs:16` объявляет `epsilon = T.CreateChecked(0.0001f)`, используемый
скалярным остатком на `:88`. `GravityService.cs:20` объявляет
`vEpsilon = new Vector<T>(T.CreateChecked(0.01f))`, используемый векторным циклом на `:65`.
Величины различаются на два порядка.

Следовательно, ускорение данного тела зависит разрывно от того, попадает ли его индекс в
векторизованный диапазон или в диапазон остатка, то есть от его положения относительно
`n - step` (`GravityService.cs:56`). Для расстояний, где `r² ≲ 0.01`, расхождение
существенно; поскольку смягчение также искажает эффективный потенциал, рассогласованность
подрывает симплектическое свойство, утверждаемое в §4.4. Сообщение последнего коммита
(`a8f6e8d`: «работает вроде но с малыми расстояниями какойто парадокс») согласуется с этим
дефектом. Исправление: вывести обе константы из одного значения. Допуск теста 1e-10 в
`Update_ThreeBodies_ConservesMomentum` к этому нечувствителен, поэтому тесты проходят.

### F-03 — Диагональные маски перевыделяются при каждом расчёте сил. **Серьёзность: средняя.**
`GravityService.cs:37–44` выделяет `Vector<T>[step]` плюс по одному `T[step]` на дорожку —
`1 + step` короткоживущих массивов — при **каждом** вызове `Update`. Поскольку `Update`
вызывается раз в подшаг (дважды в кадр при 60 FPS для `double` на AVX2), это порядка
10 аллокаций на кадр, ~600/с, и все они имеют одни и те же значения. Маски — чистая
функция от `T` и полностью кэшируемы в поле `static readonly`. Это единственный
steady-state трафик в кучу на физическом пути, и он прямо противоречит
аллокационно-свободному замыслу из §1.

### F-04 — `TrailRenderer.Render` обходит ~99 800 отрезков в кадр. **Серьёзность: средняя.**
`TrailRenderer.cs:107–127` на каждом кадре проходит всех `_maxTrails` тел и все
`_maxTrailLength - 1` слотов без какого-либо отсечения по пирамиде видимости и без
батчинга, вызывая по одному `DrawLineV` в немедленном режиме на каждую заполненную пару.
Стоимость не зависит от того, сколько следа действительно попадает на экран, и растёт с
`maxTrailLength`. Тела представлены в `System.Numerics.Vector2`, а состояние камеры
доступно, поэтому путь через пространство экрана или `rlRenderBatch` доступен без изменения
раскладки хранилища.

### F-05 — Сужение координат мира до `int` в режиме `checked` может бросить исключение. **Серьёзность: средняя.**
`EntityRenderer.cs:19` вызывает `int.CreateChecked<T>(coordX[i])`. Это усекает дробные
позиции (`DrawCircleV` в Raylib избежал бы потери) и выбрасывает `OverflowException` для
любой координаты вне `Int32` — включая `NaN` и `±Infinity`, порождённые неустойчивой
интеграцией. Тело, выброшенное из системы, превращает физическую нестабильность в падение
слоя рендеринга в том же кадре. `TrailRenderer` использует `float.CreateTruncating`
(`TrailRenderer.cs:99–100`) для тех же значений и бросить исключение не может, поэтому два
рендерера расходятся в политике переполнения.

### F-06 — Второй удар выражен как разность ускорений. **Серьёзность: средняя.**
`MovementService.cs:57–58` вычисляет `v += (a_{n+1} − a_n)·dt/2` вместо
`v = v_{n+1/2} + a_{n+1}·dt/2`. Алгебраически эквивалентно (§4.4), но сначала вычисляется
`a_{n+1} − a_n`, поэтому когда сила почти не меняется за шаг, результат есть разность
почти равных чисел и теряет значимые разряды. Каноническая форма складывает `a_{n+1}·dt/2`
со скоростью, уже содержащей полный удар, и является численно более устойчивой. Разностная
форма также делает две фазы зависимыми от порядка так, чего система типов не выражает.

### F-07 — `TrailRenderer` объявлен в глобальном пространстве имён. **Серьёзность: низкая.**
`TrailRenderer.cs:65` объявляет класс без объявления `namespace`, хотя файл расположен в
`Services/Visualization/`, и каждый соседний файл в этой папке пространство имён имеет.
Класс, следовательно, виден как глобальный `TrailRenderer` и доступен без квалификации
откуда угодно внутри сборки. Предыдущая 59-строчная реализация сохранена как
закомментированный блок на строках `:1–59` и является единственным местом, где
встречается раскладка `Vector2[][]` (рваный массив).

### F-08 — Члены расширений C# 14 не используются. **Серьёзность: низкая.**
`Extensions/Camera2DExtension.cs:11–15` объявляет `SetZoom<T>` и `SetTarget<T>`; ни у
одного нет точки вызова. `SetTarget` вдобавок вводит в заблуждение: он выполняет
`camera.Target += value` (`:14`), то есть накопление, а не присваивание. Этот файл —
единственная причина зависимости проекта от возможностей языка C# 14, то есть мёртвый
код, несущий ограничение на версию языка.

### F-09 — `MassView<T>` объявлен и не используется. **Серьёзность: низкая.**
`Components/ComponentView.cs:44–52`. `ComponentStorage.GetMasses`
(`ComponentStorage.cs:54`) вместо него возвращает голый `Span<T>`, поэтому тип представления
несогласован с тремя парными представлениями, которые действительно используются.

### F-10 — Состояние `MovementService` не проверяется между фазами. **Серьёзность: низкая.**
`MovementService.cs:35–36` пишет `_prevAccX[i]` для `i < n` в массивы, размер которых задан
аргументом конструктора (`Program.cs:13` передаёт `10000`), без проверки против
`n = world.GetActiveEntities()`. Превышение приводит к `IndexOutOfRangeException`. Более
того, если количество тел изменяется между `HalfStep` и `SecondHalf`, новые индексы
интегрируются по устаревшему или обнулённому `_prevAcc`. Требование к порядку фаз из
§4.4 документировано только последовательностью вызовов в `Program.cs:92–94`.

### F-11 — `Vector<T>(Span<T>)` копирует вместо переинтерпретации. **Серьёзность: низкая.**
`GravityService.cs:58–60` строит каждый исходный вектор через конструктор от span, который
выполняет проверку границ и поэлементное копирование. Невыровненная переинтерпретация
базового `T[]` избавила бы от копирования на каждой итерации внутреннего цикла. На
корректность не влияет.

### F-12 — Закрытие окна не выполняется. **Серьёзность: низкая.**
`WindowManager.Dispose()` (`Services/Visualization/WindowManager.cs:19`) вызывает
`CloseWindow()`, но класс не реализует `IDisposable`, и точек вызова нет — `Program.cs`
выходит из цикла и завершается без закрытия окна, полагаясь на teardown процесса.

### F-13 — `CameraController.Camera` возвращает копию структуры. **Серьёзность: низкая.**
`Services/Visualization/CameraController.cs:14` отдаёт `Camera2D` по значению; мутации со
стороны вызывающего молча отбрасываются. Строка `:15` — закомментированный `ref`-аксессор,
признающий ограничение. Текущая точка вызова только читает, поэтому дефекта на данный
момент нет, но API провоцирует его появление.

### F-14 — Число подшагов не ограничено. **Серьёзность: низкая.**
`Program.cs:83` вычисляет `subSteps = ceil(frametime / safeStep)` без верхнего предела.
Один длинный кадр — изменение размера окна, остановка в отладчике, блокирующая сборка мусора
или просто `TimeScale` на максимуме `1000` — умножает O(n²) цикл гравитации на большой
множитель и подвешивает приложение. Ограничение сверху сняло бы потолок стоимости кадра.

### F-15 — Несогласованная изменяемость span в слое рендеринга. **Серьёзность: информационная.**
`EntityRenderer.Render` принимает `Span<T>` (`EntityRenderer.cs:11`), хотя только читает, тогда
как `TrailRenderer.Update` корректно принимает `ReadOnlySpan<T>` (`TrailRenderer.cs:83`).
API хранилища также выдаёт изменяемые span без разбора (§4.1), так что ни один инвариант
компонента не защищён на границе.

### F-16 — Мёртвые локальные переменные, неиспользуемые импорты и неверные комментарии. **Серьёзность: информационная.**
Неиспользуемы: `Program.cs:10` (`var cnt = Vector<float>.Count;`),
`GravityService.cs:36` (`vLimit`), `GravityService.cs:48` (`vMassA`) и параметр
`screenHeight` в `UIService` (`UIService.cs:14`). `Program.cs:8` импортирует
`System.Runtime.Intrinsics.X86`, а несколько файлов импортируют `System.Text` /
`System.Runtime.Intrinsics` без использования. `Program.cs:47` комментирует `// =1` у
значения `0.0001`. Отдельное замечание: `WorldWidth`/`WorldHeight` (`World.cs:18–19`)
присваиваются в конструкторе и нигде не читаются — границы мира не ограничивают ни
интегрирование, ни гравитацию, поэтому тела могут покинуть номинальный мир без предела
(см. F-05).

## 8. Сборка и запуск

```bash
dotnet build SpaceGravitySimulator.slnx      # 0 ошибок, 4 предупреждения
dotnet test  SpaceGravitySimulator.slnx      # 12 пройдено, 0 не пройдено
dotnet run --project SpaceGravitySimulator/SpaceGravitySimulator.csproj
```

Проверено на SDK `10.0.401`. Четыре предупреждения:
- `CS8601` ×2 — `World.cs:20,21`: `G` и `TimeScale` инициализируются значением
  `default(T)` при ограничении `notnull`, поэтому начальные значения объявлены как
  потенциально нулевые. `TimeScale` равен `default(T)`, то есть `0.0`, пока UI его не
  запишет; поставляемый путь конструирования задаёт его в первом кадре через
  `UIService.Update`, но симуляция, запущенная без UI, интегрировала бы при
  `frametime = 0`.
- `MSTEST0037` ×2 — `Test1.cs:134,135`: использовать `Assert.IsLessThan` вместо
  `Assert.IsTrue`.

Требуется настольная система с GPU; Raylib открывает нативное окно 1000×1000 с заголовком
`Gravity Simulation` и фиксированными 60 FPS.

## 9. Итог для ревью

**Реализовано корректно и заслуживает сохранения:** раскладка SoA и API представлений на
основе `Span` образуют связный data-oriented дизайн без объектов на сущность и без
аллокаций в установившемся режиме на пути рендеринга; физическое ядро чисто отделено от
Raylib и покрывается юнит-тестами; смягчённый закон обратных квадратов, приём с
диагональными масками по золотому углу для ветвление-безопасного исключения
взаимодействия с самим собой и формулировка Velocity Verlet реализованы корректно и по
замыслу, и в арифметике.

**Требует устранения до масштабирования:** F-01 (рост ёмкости сломан для четырёх массивов
из семи — жёсткий потолок на 1024 сущности) и F-02 (две константы смягчения в одном цикле
сил) являются дефектами корректности, а не оптимизациями. F-03…F-06 — риски
производительности и устойчивости, полностью замаскированные текущим пресетом из 9 тел.
F-07…F-16 — гигиена кода.

**Основные структурные пробелы:** пул ID сущностей не имеет пути возврата (`World.cs:35`
предзаполняет 10 000 ID, а `CreateEntity` извлекает, ни разу не возвращая, поэтому
10 001-й вызов бросит исключение); слой рендеринга объявлен `internal` и не имеет
`InternalsVisibleTo`, а значит не тестируется; CI, `.editorconfig` и бенчмарк-стенд
отсутствуют — поэтому приведённые выше утверждения о производительности выведены из
анализа кода, а не из измерений. Первым делом я бы добавил BenchmarkDotNet вокруг
`GravityService.Update`, поскольку фактическая пропускная способность SIMD-пути и стоимость
F-03 сейчас не измерены.
